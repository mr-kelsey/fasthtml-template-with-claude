# CLAUDE.md

## Project Overview

A suite of family productivity applications accessible to each family member from within the LAN.  Branch focus: farm planning.

## Commands

Without Docker:
```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python main.py           # dev server with autoreload
```

With Docker Compose:
```bash
docker compose up --build   # -> http://localhost:5001
```

Tests (no external services needed):
```bash
pip install -r requirements-dev.txt
pytest                                              # full suite
pytest tests/test_db.py::test_add_note_persists_title_and_body     # single core test
pytest tests/farm/                                  # farm subdomain's suite standalone
```
Uses `.env.test` (not `.env`) via `db.Database(".env.test")`, swapped in by `tests/conftest.py` before `main`/pages are imported — truncates every table in its own db (never the real one configured in `.env`), core tables via `tests/conftest.py`'s fixtures and farm tables via `tests/farm/conftest.py`'s (pytest merges both automatically for anything under `tests/farm/`). `tests/__init__.py`/`tests/farm/__init__.py` exist so pytest's default import mode can tell `tests.test_db`/`tests.test_routes` apart from `tests.farm.test_db`/`tests.farm.test_routes`.

## Architecture

The app is split into subdomains, each free to grow its own pages/db/tests: **core** (notes, family calendar — at the repo root) and **farm** (`farm/`). A subdomain only makes sense as a split when its tables never join across the boundary — farm's tables only ever join each other, never `notes`/`calendar_events`, which is what makes the split clean rather than arbitrary. New unrelated feature areas (e.g. a future finance or chores subdomain) should follow the same `<name>/{db.py,pages/}` shape rather than growing inside `pages/` or `db.py`.

- `main.py` — builds the app, registers `init_db` as a startup hook, mounts every page module's router (`page.router.to_app(app)`) from **both** `pages.discover_page_modules()` and `farm.pages.discover_page_modules()` — no manual registration needed within either package.
- `router_discovery.py` — `discover_router_modules(package)`, the generic `iter_modules` walk (alphabetical order, submodules only, packages skipped) shared by `pages/__init__.py` and `farm/pages/__init__.py` so it isn't duplicated per subdomain. Each package still exposes its own no-arg `discover_page_modules()` calling into this with its own package.
- `pages/*.py` — one module per **core** route group (home, about, notes, calendar), each owns `router = fast.APIRouter()`. `notes.py` is the full CRUD reference (list/add/delete against SQLite).
- `farm/` — the farm-planning subdomain (see Farm Planning Plan below for what's in it):
  - `farm/db.py` — `FarmDatabaseMixin` holds farm's schema statements (`seed_varieties`/`plantings`/`land_plots`/`beds`/`farm_events`) and every farm query method. It's a pure mixin (relies on `self.engine`, never instantiates `Database` itself) composed onto the shared engine/instance in root `db.py` — see below.
  - `farm/helpers.py` — parsing/formatting helpers (`parse_agronomic_fields`, `compute_window`, etc.) for the farm pages, sibling to `family.py`/`layout.py`.
  - `farm/pages/*.py` — `farm_calendar.py`, `seed_varieties.py`, `plantings.py`, `land_plots.py`, each owning `router = fast.APIRouter()` like core pages do.
- `layout.py` — shared `layout(title, *content)` wrapper; `NAV_LINKS` drives the nav bar. Used by both core and farm pages.
- `calendar_shared.py` — presentation-generic month-grid/day-square/nav rendering (`month_grid`, `events_by_date`, `month_nav`, `day_square`, `calendar_grid`), no family/member concepts. Shared by `pages/calendar.py` (family calendar) and `farm/pages/farm_calendar.py` (farm calendar) so the two don't duplicate month-grid rendering; each page builds its own day "badges" (event bars) and hands them in. Lives at the root since both subdomains depend on it, not owned by either.
- `family.py` — loads `FAMILY_MEMBERS` (id/name/color) from `family.json` if present, else falls back to generic placeholders. `family.json` is a real, gitignored config file (like `.env`) holding the user's actual family member names — it is expected to exist and **must not** be hardcoded into `family.py` or any tracked file; `family.example.json` is only the checked-in template.
- `db.py` — `_CoreDatabase` class owns one SQLAlchemy `engine` (`sqlite:///{DB_PATH}`), `init_db`, and the core (notes/calendar_events/recurring_events) schema/queries (`text()` + bound `:params`); `connect_args={"check_same_thread": False}` is required since Starlette runs sync handlers in a thread pool. The concrete `Database(FarmDatabaseMixin, _CoreDatabase)` class, defined at the bottom of this file, composes farm's schema/queries in via multiple inheritance and concatenates both `SCHEMA_STATEMENTS` lists so one `init_db()` call creates every table. A module-level `_instance` (default `Database()`) is what `db.list_notes()`, `db.add_planting()`, `db.engine`, etc. actually resolve to, via a module `__getattr__` — this lets `tests/conftest.py` swap `db._instance` to a `Database(".env.test")` before `main`/pages import, with zero changes needed in the callers (they always go through `db.<name>`, never bind it early). Callers never need to know or care that a method came from the core class vs. the farm mixin.
- New core page: create `pages/foo.py` with its own `router` — it's picked up automatically on next run/import. New farm page: same, but under `farm/pages/foo.py`. Optionally link it in `layout.py`'s `NAV_LINKS`.

## Farm Planning Plan

Original goal: plan crops/beds on the newly-purchased land, track germination timing for succession planting, and log weather/precipitation. That's now expanding toward a **yield-prediction initiative**: collect enough structured data per planting (genetics, soil, feeding, siting, weather, timing) to eventually train a model predicting harvest weight (lb) from growing conditions. Every phase below is data-collection infrastructure in service of that goal.

**Status quo (implemented — see git history for full design rationale)**: farm calendar (`farm_events`, auto-generated germination-check/harvest reminders), seed variety + planting CRUD (`seed_varieties`/`plantings`, flat no-inheritance schema), duplicate-variety convenience, succession-overlap warning by free-text location, interactive land map with drag/resize beds (`land_plots`/`beds`, `static/land-map.js`), per-square-foot bed detail view with interplanting support, and the farm/core subdomain split (`farm/db.py`, `farm/helpers.py`, `farm/pages/`, `tests/farm/`).

The following phases are the plan for the data-collection rework, roughly in dependency order:

- **0. Schema-evolution foundation**: every farm table so far has only ever grown via new `CREATE TABLE IF NOT EXISTS` statements — nothing has altered an existing table's columns yet, and several phases below need to (new columns on `seed_varieties`/`plantings`). SQLite (≥3.35) supports `ALTER TABLE t ADD COLUMN IF NOT EXISTS c ...`, just as idempotent as `CREATE TABLE IF NOT EXISTS` — so new columns are added as more statements appended to the existing `SCHEMA_STATEMENTS` list (after their table's `CREATE TABLE`), no separate migration framework needed.

- **1. Seed data model — soil/feeding/shade + seeds-on-hand as inventory, not catalog data**: add `soil_type`, `soil_ph_min`/`soil_ph_max`, `feeding_frequency_days`, `feeding_npk_n`/`feeding_npk_p`/`feeding_npk_k` (numeric N-P-K, not a free-text formula string, so it's usable as a model feature) to `seed_varieties`. On "shade tolerance (maybe already handled in sun needs?)": fold it into `sun_needs` rather than adding a new column — redefine `sun_needs`'s value domain to the ordinal `full_sun`/`partial_shade`/`full_shade` (the *minimum* light the plant tolerates), which is the same axis as "how much shade can it take" viewed from the other end, and is also the exact vocabulary phase 7's shade classifier needs to compare against. On "seed age": that's a property of the physical seed packet on hand, not of the variety (a variety is timeless catalog data; a packet has a pack/purchase date) — conflating the two was the one domain slip in the request. Add a `seed_lots` table instead (`id`, `variety_id` FK, `quantity_on_hand`, `acquired_date`, `seed_source`, `notes`) representing inventory, and `plantings.seed_lot_id` (nullable FK) recording which physical lot was sown — this also covers the old "seed inventory + observed germination rate over time" deferred item, folded in here rather than staying separate.

- **2. Companion/antagonist rules**: new `companion_rules` table (`plant_a_common_name`, `plant_b_common_name`, `relation` CHECK IN `('companion','antagonist')`, `notes`) keyed by `common_name`, not `variety_id` — companion-planting folklore is expressed at the crop level ("tomatoes and basil"), not down to cultivar ("Cherokee Purple and Genovese"), matching the reasoning that already collapsed `seed_varieties` away from taxonomic inheritance. Simple list/add/delete CRUD, folded into `farm/pages/seed_varieties.py` rather than a new page module (small, no map/geometry of its own).

- **3. Bed-planting flow rework — variety-first cell stamping**: currently the bed grid is cell-first (click a cell, then choose what goes in it). Flip it: the bed detail page gets a variety palette sidebar; selecting a variety arms it, and each subsequent cell click stamps that variety into a client-side staged set (new `static/bed-detail.js`, same hand-rolled-JS-exception pattern as `land-map.js` — htmx can't do live per-click spacing/companion computation without a round trip per click). A "Plant staged cells" form at the end sets the fields shared by the whole batch — `planted_date`, `source_type` (`seed`/`transplant`), `soil_temp_f` — and POSTs once to a new `/beds/{id}/cells/batch` route that creates one `plantings` row per staged cell (mirrors today's one-row-per-cell model, just batched instead of one POST per cell).
  - *Spacing guard*: computed client-side from the selected variety's `spacing_in` and the bed's existing + currently-staged same-variety cells. Convert inches to a whole-cell block radius: `radius = max(0, ceil(spacing_in / 12) - 1)`, then block every cell within Chebyshev distance ≤ `radius` of any same-variety cell (a square neighborhood, not a circle — matches the worked 24"-spacing example exactly: radius 1 blocks the 8 surrounding cells). Bed-edge/corner cells naturally block fewer neighbors once the blocked set is clipped to the bed's own bounds — no special-casing needed. Only blocks the *same* variety; a different variety may still take a blocked cell. Scoped to one bed — no cross-bed proximity, since that needs real map-space geometry between beds, not just one bed's grid (added to deferred list).
  - *Companion/antagonist highlight*: for the armed variety, cross-reference every already-occupied cell (persisted or staged) against `companion_rules` by common name; tint companion cells green, antagonist cells red (low-opacity overlay, not a block).
  - *Transplant lineage*: `plantings` gains `source_type` (default `'seed'`), `transplant_origin_planting_id` (nullable self-FK — "grown from this other planting"), `starter_source`/`starter_vendor`/`starter_purchased_date` (nullable, for a purchased starter with no origin planting), and `soil_temp_f`. Maturity-window math stays keyed off `planted_date` unchanged — seed packets already list days-to-maturity counted from transplant date for transplanted crops, not from sowing, so no formula change is needed. What "drag over the maturity date timeline" really calls for is a lineage view, not different math: add `GET /plantings/{id}/lineage` chaining backward through `transplant_origin_planting_id` and forward through any plantings that originated from it.

- **4. Feeding/treatment product tracking**: garden inputs aren't only fertilizers — soaps, mildew inhibitors, etc. also get applied on a schedule — so this needs a product catalog plus an application log, not just NPK numbers bolted onto `seed_varieties`. New `garden_products` table: `name`, `product_type` (free text, suggested vocabulary fertilizer/pesticide/fungicide/soap/other — not CHECK-constrained, since new categories will keep coming up and nothing downstream needs to branch on it), `npk_n`/`npk_p`/`npk_k` (nullable — only meaningful for fertilizers), `benefit_notes` (free text — what a non-NPK product like a soap or mildew inhibitor is *for*), `application_frequency_days` (how often it should be reapplied). New `product_applications` table logs each actual use: `product_id` FK, `applied_date`, `bed_id` (nullable) + `location` (free text) targeting — the same flexible bed-or-free-text pattern `plantings` already uses, rather than inventing another targeting mechanism — `amount`, `unit` (free text, e.g. "cups"/"gal"/"oz"), `notes`.
  - This is deliberately separate from `seed_varieties.feeding_frequency_days`/`feeding_npk_*` (phase 1): the variety fields are *agronomic guidance* — what a plant generally wants, independent of any specific product — while `garden_products`/`product_applications` is the *actual record* of what was done and when. Both matter for the prediction model; the gap between intended and actual feeding is itself a potential feature.
  - Reminders: after logging an application, recompute the next-due reminder for that exact `(product_id, bed_id, location)` target — `applied_date + application_frequency_days` — as a `farm_events` row (new `event_type` `'product-reminder'`, needs a `farm_events.linked_product_application_id` column added in phase 0's schema-evolution pass, mirroring `linked_planting_id`'s anchor-row pattern rather than inventing a new linkage style). Regenerating the reminder on each new application supersedes the prior one for that target, the same idea `_regenerate_bed_farm_events` already uses for superseding old rows on edit.

- **5. Farm-event grouping simplification**: replace the adjacency-based `_connected_components` clustering in `farm/db.py` with a flat group-by-`(variety_id, planted_date)` across *all* plantings, bed-placed or not — "same variety, same day" should be one calendar reminder regardless of placement, which is both what was asked for and a net simplification (deletes `_connected_components` and collapses the two separate `_regenerate_farm_events`/`_regenerate_bed_farm_events` code paths into one). Germination-check generation is additionally gated on `source_type == 'seed'` — a transplant already germinated somewhere else (or was purchased), so there's nothing to check on-site.

- **6. Germination-rate + harvest-weight logging**: the farm calendar's `germination-check` and `harvest` events become actionable instead of read-only — clicking one opens a small form (germination-check: sets `quantity_germinated` on the group's plantings; harvest: logs a row to a new `harvests` table — `planting_id` FK to the group's anchor planting, `harvest_date`, `weight_lb`, `notes` — rather than a single field, since one planting can be picked multiple times, e.g. tomatoes over weeks, and total yield is a sum, not a single number). **This wasn't explicitly requested, but it's the other half of the stated end goal**: a yield-prediction model needs a labeled outcome (pounds harvested) alongside the input features the rest of this plan collects — without this phase, every other phase builds the X and never the y.

- **7. Shade polygons + sun/shade-aware planting warnings**: new `shade_sources` (`plot_id` FK, `label`) → `shade_polygons` (`shade_source_id` FK, `season` CHECK IN `('summer_solstice','winter_solstice')`, `shade_type` CHECK IN `('full','partial')`, `points` — JSON array of `[x, y]` plot-foot floats; SQLite has no native geometry type, so JSON text matches the app's plain-SQLite style) — up to 4 polygons per source (full/partial × summer/winter), drawn freehand on the land map via a new drawing mode in the map JS (click to add vertex, close on first-vertex click, drag to adjust). For a given date, true polygon-shape interpolation between the two solstice snapshots isn't well-defined for arbitrary user-drawn shapes with different vertex counts, so instead of morphing geometry, classify each cell against whichever solstice is nearer in the annual cycle (circular day-of-year distance, crossing over at the equinoxes) — this still delivers "grows toward winter, shrinks toward summer" without needing vertex correspondence. New `farm/geometry.py`: ray-casting point-in-polygon, bed-cell → plot-space transform (reusing the same translate+rotate the map SVG already applies), and `classify_bed_cell_shade(bed, cell_x, cell_y, on_date)` returning `full_sun`/`partial_shade`/`full_shade` (darkest source wins when several overlap a cell). Used in two places: a shade tint on the bed detail grid for "today" (or a picked date), and a planting-time warning in phase 3's cell-stamping flow — sample the classifier weekly across the variety's expected `planted_date` → maturity-window-end range and warn if any sample exceeds the variety's `sun_needs` tolerance.

- **Deferred/overlooked items to revisit**: weather/precipitation API ingestion, frost-date-based planting validation, crop rotation history by plant family, cross-bed spacing/companion proximity (needs real map-space geometry between beds, not just one bed's grid), seed-lot inventory auto-decrement on planting, mobile-friendly bed entry, printable/exportable seasonal planting calendar, task list (harden off seedlings, thin rows, start indoors) generated from planting dates, photo attachment per bed, multi-year bed history view for rotation planning, bed resize-handle hit target may be too small on large plots (handle is a flat 1ft square regardless of zoom), exporting the accumulated planting/harvest/weather dataset (CSV/parquet) once enough seasons exist — the actual model training is out of scope for this app.
