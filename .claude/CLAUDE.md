# CLAUDE.md

## Project Overview

A suite of family productivity applications accessible to each family member from within the LAN.  Branch focus: farm planning.

## Commands

Without Docker:
```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python main.py           # dev server with autoreload
```

With Docker Compose:
```bash
docker compose up --build   # -> http://localhost:5001
```

Tests (no external services needed):
```bash
pip install -r requirements-dev.txt
pytest                                              # full suite
pytest tests/test_db.py::test_add_note_persists_title_and_body     # single core test
pytest tests/farm/                                  # farm subdomain's suite standalone
```
Uses `.env.test` (not `.env`) via `db.Database(".env.test")`, swapped in by `tests/conftest.py` before `main`/pages are imported — truncates every table in its own db (never the real one configured in `.env`), core tables via `tests/conftest.py`'s fixtures and farm tables via `tests/farm/conftest.py`'s (pytest merges both automatically for anything under `tests/farm/`). `tests/__init__.py`/`tests/farm/__init__.py` exist so pytest's default import mode can tell `tests.test_db`/`tests.test_routes` apart from `tests.farm.test_db`/`tests.farm.test_routes`.

`tests/farm/test_land_map_js.py`/`test_bed_detail_js.py` drive the hand-rolled `static/land-map.js`/`bed-detail.js` for real, via Playwright against a live `main.app` (`tests/farm/conftest.py`'s `live_server_url`/`browser`/`page` fixtures — a real `uvicorn.Server` in a background thread, sharing the same `.env.test` engine, so the existing per-test cleanup fixtures still apply). Needs `playwright install chromium` once if not already installed.

## Architecture

The app is split into subdomains, each free to grow its own pages/db/tests: **core** (notes, family calendar — at the repo root) and **farm** (`farm/`). A subdomain only makes sense as a split when its tables never join across the boundary — farm's tables only ever join each other, never `notes`/`calendar_events`, which is what makes the split clean rather than arbitrary. New unrelated feature areas (e.g. a future finance or chores subdomain) should follow the same `<name>/{db.py,pages/}` shape rather than growing inside `pages/` or `db.py`.

- `main.py` — builds the app, registers `init_db` as a startup hook, mounts every page module's router (`page.router.to_app(app)`) from **both** `pages.discover_page_modules()` and `farm.pages.discover_page_modules()` — no manual registration needed within either package.
- `router_discovery.py` — `discover_router_modules(package)`, the generic `iter_modules` walk (alphabetical order, submodules only, packages skipped) shared by `pages/__init__.py` and `farm/pages/__init__.py` so it isn't duplicated per subdomain. Each package still exposes its own no-arg `discover_page_modules()` calling into this with its own package.
- `pages/*.py` — one module per **core** route group (home, about, notes, calendar), each owns `router = fast.APIRouter()`. `notes.py` is the full CRUD reference (list/add/delete against SQLite).
- `farm/` — the farm-planning subdomain (see Farm Planning Plan below for what's in it):
  - `farm/db.py` — `FarmDatabaseMixin` holds farm's schema statements (`seed_varieties`/`plantings`/`land_plots`/`beds`/`farm_events`) and every farm query method. It's a pure mixin (relies on `self.engine`, never instantiates `Database` itself) composed onto the shared engine/instance in root `db.py` — see below.
  - `farm/helpers.py` — parsing/formatting helpers (`parse_agronomic_fields`, `compute_window`, etc.) for the farm pages, sibling to `family.py`/`layout.py`.
  - `farm/pages/*.py` — `farm_calendar.py`, `seed_varieties.py`, `plantings.py`, `land_plots.py`, each owning `router = fast.APIRouter()` like core pages do.
- `layout.py` — shared `layout(title, *content)` wrapper; `NAV_LINKS` drives the nav bar. Used by both core and farm pages.
- `calendar_shared.py` — presentation-generic month-grid/day-square/nav rendering (`month_grid`, `events_by_date`, `month_nav`, `day_square`, `calendar_grid`), no family/member concepts. Shared by `pages/calendar.py` (family calendar) and `farm/pages/farm_calendar.py` (farm calendar) so the two don't duplicate month-grid rendering; each page builds its own day "badges" (event bars) and hands them in. Lives at the root since both subdomains depend on it, not owned by either.
- `family.py` — loads `FAMILY_MEMBERS` (id/name/color) from `family.json` if present, else falls back to generic placeholders. `family.json` is a real, gitignored config file (like `.env`) holding the user's actual family member names — it is expected to exist and **must not** be hardcoded into `family.py` or any tracked file; `family.example.json` is only the checked-in template.
- `db.py` — `_CoreDatabase` class owns one SQLAlchemy `engine` (`sqlite:///{DB_PATH}`), `init_db`, and the core (notes/calendar_events/recurring_events) schema/queries (`text()` + bound `:params`); `connect_args={"check_same_thread": False}` is required since Starlette runs sync handlers in a thread pool. The concrete `Database(FarmDatabaseMixin, _CoreDatabase)` class, defined at the bottom of this file, composes farm's schema/queries in via multiple inheritance and concatenates both `SCHEMA_STATEMENTS` lists so one `init_db()` call creates every table. A module-level `_instance` (default `Database()`) is what `db.list_notes()`, `db.add_planting()`, `db.engine`, etc. actually resolve to, via a module `__getattr__` — this lets `tests/conftest.py` swap `db._instance` to a `Database(".env.test")` before `main`/pages import, with zero changes needed in the callers (they always go through `db.<name>`, never bind it early). Callers never need to know or care that a method came from the core class vs. the farm mixin.
- New core page: create `pages/foo.py` with its own `router` — it's picked up automatically on next run/import. New farm page: same, but under `farm/pages/foo.py`. Optionally link it in `layout.py`'s `NAV_LINKS`.

## Farm Planning Plan

Original goal: plan crops/beds on the newly-purchased land, track germination timing for succession planting, and log weather/precipitation. That's now expanding toward a **yield-prediction initiative**: collect enough structured data per planting (genetics, soil, feeding, siting, weather, timing) to eventually train a model predicting harvest weight (lb) from growing conditions. Every phase below is data-collection infrastructure in service of that goal.

**Status quo (implemented — see git history for full design rationale)**: farm calendar (`farm_events`, auto-generated germination-check/harvest reminders), seed variety + planting CRUD (`seed_varieties`/`plantings`, flat no-inheritance schema), duplicate-variety convenience, succession-overlap warning by free-text location, interactive land map with drag/resize beds (`land_plots`/`beds`, `static/land-map.js`), per-square-foot bed detail view with interplanting support, and the farm/core subdomain split (`farm/db.py`, `farm/helpers.py`, `farm/pages/`, `tests/farm/`).

The following phases are the plan for the data-collection rework, roughly in dependency order:

- **0. Schema-evolution foundation** (done): every farm table so far had only ever grown via new `CREATE TABLE IF NOT EXISTS` statements — nothing had altered an existing table's columns yet, and several phases below need to (new columns on `seed_varieties`/`plantings`). Unlike `CREATE TABLE`, SQLite's `ALTER TABLE ... ADD COLUMN` has no `IF NOT EXISTS` clause — verified directly against the sqlite3 module (`ALTER TABLE t ADD COLUMN IF NOT EXISTS c ...` raises `near "EXISTS": syntax error`), so idempotency can't be pushed into the SQL string the way `CREATE TABLE IF NOT EXISTS` does it. Instead, `db.py`'s `add_column_if_not_exists(db_connection, table, column, coldef)` checks `PRAGMA table_info(table)` first and only runs the `ALTER TABLE` if the column is missing. `SCHEMA_STATEMENTS` entries are now either a plain SQL string (`CREATE TABLE ...`) or a `(table, column, coldef)` tuple for an additive column; `_CoreDatabase.init_db()` dispatches on the entry's type. Still no separate migration framework — new columns are still just appended to the existing `SCHEMA_STATEMENTS` list (after their table's `CREATE TABLE`), just as a tuple instead of a raw `ALTER TABLE` string.

- **1. Seed data model — soil/feeding/shade + seeds-on-hand as inventory, not catalog data**: add `soil_type`, `soil_ph_min`/`soil_ph_max`, `feeding_frequency_days`, `feeding_npk_n`/`feeding_npk_p`/`feeding_npk_k` (numeric N-P-K, not a free-text formula string, so it's usable as a model feature) to `seed_varieties`. On "shade tolerance (maybe already handled in sun needs?)": fold it into `sun_needs` rather than adding a new column — redefine `sun_needs`'s value domain to the ordinal `full_sun`/`partial_shade`/`full_shade` (the *minimum* light the plant tolerates), which is the same axis as "how much shade can it take" viewed from the other end, and is also the exact vocabulary phase 9's shade classifier needs to compare against. On "seed age": that's a property of the physical seed packet on hand, not of the variety (a variety is timeless catalog data; a packet has a pack/purchase date) — conflating the two was the one domain slip in the request. Add a `seed_lots` table instead (`id`, `variety_id` FK, `quantity_on_hand`, `acquired_date`, `seed_source`, `notes`) representing inventory, and `plantings.seed_lot_id` (nullable FK) recording which physical lot was sown — this also covers the old "seed inventory + observed germination rate over time" deferred item, folded in here rather than staying separate.

- **2. Companion/antagonist rules**: new `companion_rules` table (`plant_a_common_name`, `plant_b_common_name`, `relation` CHECK IN `('companion','antagonist')`, `notes`) keyed by `common_name`, not `variety_id` — companion-planting folklore is expressed at the crop level ("tomatoes and basil"), not down to cultivar ("Cherokee Purple and Genovese"), matching the reasoning that already collapsed `seed_varieties` away from taxonomic inheritance. Simple list/add/delete CRUD, folded into `farm/pages/seed_varieties.py` rather than a new page module (small, no map/geometry of its own).

- **3. Continuous inch-resolution plant positioning**: `plantings.x_in`/`y_in` (float, inches from the bed's origin corner) are the sole authoritative position — a 12" cell grid can't represent real planting practice for any spacing that isn't a multiple of 12" (e.g. 16" spacing along a 48" row fits 4 plants, but snapping to 12" cell boundaries collapses that to 2 usable slots). Anywhere the app groups by cell (interplanting display, companion/antagonist adjacency) buckets by `floor(x_in / 12)`/`floor(y_in / 12)`, computed rather than stored. The 12" grid remains the *visual* backdrop for the bed detail view (a scale reference and interplanting's per-square grouping), it just isn't the *unit of placement* — this gives plantings-within-a-bed the same continuous positioning `land-map.js` already uses for beds-within-a-plot. Blocks phase 5 below, which is what actually needs real positions to compute a correct spacing guard.

- **4. Seed & transplant inventory gating + provenance**: phase 1's `seed_lots` has `quantity_on_hand` but nothing consumes it yet, and there's no equivalent inventory for raised or purchased transplants — yet the planting flow fundamentally needs both: direct sow should only offer varieties with seed stock on hand, transplant should only offer varieties with transplant stock on hand. The two are gated differently, deliberately: transplant stock is an exact, hard cap (you cannot plant more seedlings than you raised or bought), while seed-packet counts are an approximate bulk quantity gardeners routinely sow against loosely (thin later) — so direct-sow gating stays existence-only ("do we have any seed on hand"), not quantity-exact. Exact seed decrement is now implemented, but only for phase 5's batch-stamping flow (a "seeds per location" figure entered once per batch, multiplied by the staged point count) — the plain single-planting form (`/plantings`) has no lot concept and still doesn't decrement anything. New `transplant_lots` table, same shape as `seed_lots`: `id`, `variety_id` FK, `quantity_on_hand`, `origin_planting_id` (nullable FK to `plantings` — the indoor/nursery seed-starting row these were raised from), `purchased_source`/`purchased_vendor`/`purchased_date` (nullable, for a store-bought flat with no origin planting), `notes`. This supersedes the `transplant_origin_planting_id`/`starter_source`/`starter_vendor`/`starter_purchased_date` columns an earlier draft of the bed-planting-flow phase put directly on `plantings`: that provenance belongs to the *lot* — a tray of a dozen seedlings raised or bought together shares one origin, not one copy per seedling — not to each individual bed-planting drawn from it. `plantings` only needs `transplant_lot_id` (nullable FK) plus `source_type` (`seed`/`transplant`, default `'seed'`, moved up from that same earlier draft since phase 5's mode toggle needs it to already exist). Neither `seed_lots` nor `transplant_lots` has a CRUD surface yet — this phase adds one, a new `farm/pages/inventory.py` (list/add/edit/delete for both, small forms, no map/geometry of its own — same reasoning that folded companion rules into `seed_varieties.py` in phase 2). `transplant_lots.quantity_on_hand` decrements server-side when a transplant-mode batch is planted (mechanics in phase 5); `seed_lots.quantity_on_hand` likewise decrements for a seed-mode batch, drawn down oldest-`acquired_date`-lot-first across the variety's lots and clamped at zero per lot (see phase 5's batch flow) -- gating itself stays existence-only, per above.

- **5. Bed-planting flow rework — variety-first lattice stamping**: currently the bed grid is cell-first (click a cell, then choose what goes in it). Flip it: the bed detail page gets a variety palette sidebar with a direct-sow/transplant mode toggle that filters it to varieties with matching inventory (direct sow: any `seed_lots` row for the variety; transplant: any `transplant_lots` row with `quantity_on_hand` > 0 — phase 4). Selecting a variety arms it and renders that variety's spacing lattice — points at `spacing_in` intervals in both axes, fenceposted from the bed's origin corner (phase 3's `x_in`/`y_in`, not the 12" cell grid) — as clickable targets over the bed; each click stamps the variety at that point into a client-side staged set, drawn as a dot in the variety's own color (new `seed_varieties.color_hex`, auto-assigned from a fixed palette at creation, editable on the variety form — same id/name/color shape `family.py`'s `FAMILY_MEMBERS` already uses) so staged and already-planted points of different varieties read apart at a glance (new `static/bed-detail.js`, same hand-rolled-JS-exception pattern as `land-map.js` — htmx can't do live per-click spacing/companion/inventory computation without a round trip per click). A "Plant staged points" form at the end sets the fields shared by the whole batch — `planted_date`, `soil_temp_f`, in seed mode a single "seeds per location" count applied to every staged point's `quantity`, and in transplant mode which `transplant_lot_id` they're drawn from — and POSTs once to a new `/beds/{id}/cells/batch` route that creates one `plantings` row per staged point and, in transplant mode, decrements that lot's `quantity_on_hand` by the count planted (in seed mode, draws down the variety's `seed_lots` by staged-point-count × seeds-per-location instead — see phase 4).
  - *Spacing guard*: computed client-side from the selected variety's `spacing_in` and the bed's existing + currently-staged same-variety points' real `x_in`/`y_in` (phase 3). For each lattice point, block it if the true Euclidean distance to any same-variety point is less than `spacing_in` — this replaces an earlier draft of this phase that blocked whole cells within a Chebyshev radius of `ceil(spacing_in/12)-1`, which quantized positions to the 12" grid (understating real capacity for any non-multiple-of-12 spacing — 16" spacing in a 48" row worked out to 2 plants instead of the achievable 4) and over-blocked diagonal neighbors regardless of their true distance. Lattice points outside the bed's bounds are simply not offered — no separate edge-clipping logic needed. Only blocks the *same* variety; a different variety may still take a blocked point. Scoped to one bed — no cross-bed proximity, since that needs real map-space geometry between beds, not just one bed's grid (stays on the deferred list).
  - *Companion/antagonist highlight*: for the armed variety, cross-reference every already-occupied point (persisted or staged) against `companion_rules` by common name; tint companion points green, antagonist points red (low-opacity overlay, not a block).
  - *Transplant stock gating*: in transplant mode, staging is capped at the armed variety's lot's remaining `quantity_on_hand` (already-staged this session counts against it) — a hard block, since you can't stage a seedling that doesn't exist. Submitting the batch with staged count *below* the lot's on-hand quantity triggers a non-blocking confirmation ("N left in this lot — plant them too, or is the count off?"). Both the hard-block and the under-count confirmation surface the same inline quantity-on-hand edit — a small editable field on the palette's armed-variety row, no page navigation — so a stale count can be corrected in place, whether it was recorded too low (raising the cap) or too high (the under-count warning was actually correct, just update it and move on).
  - *Lineage*: with provenance now living on `transplant_lots` (phase 4) rather than on each `plantings` row, `GET /plantings/{id}/lineage` for a transplant-mode planting walks `transplant_lot_id → transplant_lots.origin_planting_id` to find the nursery/seed-starting planting, if self-grown, and `GET /transplant_lots/{id}/plantings` lists every bed-planting drawn from that lot — the same "drag over the maturity date timeline" need an earlier draft solved with a direct planting-to-planting self-FK, just anchored on the shared lot instead. Maturity-window math still keys off `planted_date` unchanged — seed packets already count days-to-maturity from transplant date for transplanted crops, not from sowing.

- **6. Feeding/treatment product tracking**: garden inputs aren't only fertilizers — soaps, mildew inhibitors, etc. also get applied on a schedule — so this needs a product catalog plus an application log, not just NPK numbers bolted onto `seed_varieties`. New `garden_products` table: `name`, `product_type` (free text, suggested vocabulary fertilizer/pesticide/fungicide/soap/other — not CHECK-constrained, since new categories will keep coming up and nothing downstream needs to branch on it), `npk_n`/`npk_p`/`npk_k` (nullable — only meaningful for fertilizers), `benefit_notes` (free text — what a non-NPK product like a soap or mildew inhibitor is *for*), `application_frequency_days` (how often it should be reapplied). New `product_applications` table logs each actual use: `product_id` FK, `applied_date`, `bed_id` (nullable) + `location` (free text) targeting — the same flexible bed-or-free-text pattern `plantings` already uses, rather than inventing another targeting mechanism — `amount`, `unit` (free text, e.g. "cups"/"gal"/"oz"), `notes`.
  - This is deliberately separate from `seed_varieties.feeding_frequency_days`/`feeding_npk_*` (phase 1): the variety fields are *agronomic guidance* — what a plant generally wants, independent of any specific product — while `garden_products`/`product_applications` is the *actual record* of what was done and when. Both matter for the prediction model; the gap between intended and actual feeding is itself a potential feature.
  - Reminders: after logging an application, recompute the next-due reminder for that exact `(product_id, bed_id, location)` target — `applied_date + application_frequency_days` — as a `farm_events` row (new `event_type` `'product-reminder'`, needs a `farm_events.linked_product_application_id` column added in phase 0's schema-evolution pass, mirroring `linked_planting_id`'s anchor-row pattern rather than inventing a new linkage style). Regenerating the reminder on each new application supersedes the prior one for that target, the same idea `_regenerate_bed_farm_events` already uses for superseding old rows on edit.

- **7. Farm-event grouping simplification**: replace the adjacency-based `_connected_components` clustering in `farm/db.py` with a flat group-by-`(variety_id, planted_date)` across *all* plantings, bed-placed or not — "same variety, same day" should be one calendar reminder regardless of placement, which is both what was asked for and a net simplification (deletes `_connected_components` and collapses the two separate `_regenerate_farm_events`/`_regenerate_bed_farm_events` code paths into one). Germination-check generation is additionally gated on `source_type == 'seed'` — a transplant already germinated somewhere else (or was purchased), so there's nothing to check on-site.

- **8. Germination-rate, culling, and harvest-weight logging — full seed-to-harvest quantity tracking**: the farm calendar's `germination-check` and `harvest` events become actionable instead of read-only — clicking one opens a small form (germination-check: sets `quantity_germinated` on the group's plantings; harvest: logs a row to a new `harvests` table — `planting_id` FK to the group's anchor planting, `harvest_date`, `weight_lb`, `notes` — rather than a single field, since one planting can be picked multiple times, e.g. tomatoes over weeks, and total yield is a sum, not a single number). Thinning/culling isn't calendar-driven the way germination checks and harvests are (nothing to remind about — it happens whenever the bed looks crowded), so it's a plain editable field rather than a farm-event form: `plantings.quantity_culled` (new column, validated ≤ `quantity_germinated`), settable from the planting's own detail/edit view. Living plant count is then `quantity_germinated - quantity_culled`, and yield per plant — `SUM(harvests.weight_lb) / living plant count` — is a computed display value (not stored) shown alongside a planting's harvest history: 12 sown, 10 germinated, 4 culled leaves 6 living; 6 lb harvested is 1 lb/plant. **This wasn't explicitly requested, but it's the other half of the stated end goal**: a yield-prediction model needs a labeled outcome (pounds harvested, ideally per-plant) alongside the input features the rest of this plan collects — without this phase, every other phase builds the X and never the y.

- **9. Shade polygons + sun/shade-aware planting warnings**: `shade_sources` (`plot_id` FK, `label`) → `shade_polygons` (`shade_source_id` FK, `season` CHECK IN `('summer_solstice','winter_solstice')`, `shade_type` CHECK IN `('full','partial')`, `points` — JSON array of `[x, y]` plot-foot floats, clamped to the plot's bounds; SQLite has no native geometry type, so JSON text matches the app's plain-SQLite style) — up to 4 polygons per source (full/partial × summer/winter), drawn freehand on the land map (click to add vertex, close on first-vertex click, drag to adjust, all clamped to the plot edge). The sidebar arms one shade type at a time (Full or Partial), each requiring both seasons to be drawn (edited independently once both exist) — a shape needs both its summer and winter extent to mean anything. `farm/geometry.py`: ray-casting point-in-polygon, bed-local x/y → plot-space transform (reusing the same translate+rotate the map SVG already applies), `signed_distance_to_polygon` (distance to nearest edge, positive inside), and a continuous `_season_weight(on_date)` (cosine curve, 1.0 at the summer solstice, 0.0 at the winter solstice, ~0.5 at both equinoxes) that linearly blends each shade type's summer/winter signed distances before testing "inside" — so shade grows and shrinks gradually across the year rather than snapping between two states. `classify_bed_cell_shade(bed, x_in, y_in, on_date, shade_polygons)` returns `full_sun`/`partial_shade`/`full_shade` (darkest source wins when several overlap a point — uses phase 3's real `x_in`/`y_in`). Used in two places: a shade tint on the bed detail grid for "today" (or a picked date), and a planting-time warning in phase 5's lattice-stamping flow — sample the classifier weekly across the variety's expected `planted_date` → maturity-window-end range and warn if any sample exceeds the variety's `sun_needs` tolerance. `beds` has no separate `sun_exposure`/`irrigation_zone` labels — the shade classifier is the only source of truth for light, and there's no irrigation-tracking feature.

- **Deferred/overlooked items to revisit**: weather/precipitation API ingestion, frost-date-based planting validation, crop rotation history by plant family, cross-bed spacing/companion proximity (needs real map-space geometry between beds, not just one bed's grid), hiding zero-on-hand seed/transplant lots from pickers once phase 4's inventory views get cluttered with depleted stock, mobile-friendly bed entry, printable/exportable seasonal planting calendar, task list (harden off seedlings, thin rows, start indoors) generated from planting dates, photo attachment per bed, multi-year bed history view for rotation planning, bed resize-handle hit target may be too small on large plots (handle is a flat 1ft square regardless of zoom), exporting the accumulated planting/harvest/weather dataset (CSV/parquet) once enough seasons exist — the actual model training is out of scope for this app.
